# D003 critical 可靠性目标分层

- 状态：已确认
- 确认人：wenye.zhang（项目负责人）
- 确认日期：2026-10-12
- 触发：T02（POC-1 投递可靠性）按任务卡要求升级（风险 R02）

## 问题

C07 的可靠性目标是「critical 事件丢失率不超过 0.1%」（`docs/decisions/D001-scope.md` 的已知代价、T16 任务卡、`docs/contracts/receiver-requirements.md` 都引用它）。T02 的 POC-1 用真实浏览器实测后确认：**这个目标在「浏览器强杀」场景下无法通过「critical 预写 + 补发」达成**。

## 证据（POC-1，三引擎 × 四类场景，每格 ≥1000 条样本）

`docs/poc/POC-1.md`，原始数据在 `poc/poc-1/results/` 与 `poc/poc-1/results-firefox/`：

| 场景 | critical 丢失率 | 说明 |
|---|---|---|
| 页面离开（`pagehide` / `visibilitychange` × beacon / keepalive） | **0%**（Chromium、Firefox 四格各 0/1000） | WebKit 的 `visibilitychange` 两格因 headless 下触发未发生，不计入路径结论 |
| 断网（同页恢复 / 刷新后恢复） | **0%** | 刷新路径的 normal 为 100% 丢（normal 不持久化） |
| 多标签页（三种选主方式 + 不选主） | **0%** | 选主只影响重复量，不影响丢失 |
| 优雅关闭（`page.close` / `context.close` / `browser.close`） | **0%** | 预写全部存活 |
| **强杀（SIGKILL）延迟 0 / 250 / 1000 / 2500 / 4000 ms** | **Chromium 100%、Firefox 100%**；WebKit 0% | 预写在 Chromium/Firefox 上 0/1000 落盘 |
| 强杀延迟 5000 ms | Chromium 0%；**Firefox 仍丢 20%** | Firefox 的落盘窗口比 Chromium 更宽 |

补充事实：三次独立运行在 1000–4000 ms 的存活率为 **0% / 20% / 0%**，说明落盘窗口边界**不确定**，不能当作常数；根因是 `localStorage` 的写入并非同步持久化（POC 只测了 localStorage，IndexedDB/OPFS 未测）。

结论：**「critical 预写」不能作为强杀兜底。**

## 结论（分层目标）

1. **有优雅退出路径的场景**（页面离开或隐藏、断网后恢复、多标签页、优雅关闭）：`critical 丢失率 ≤ 0.1%` **继续适用**，POC 实测为 0%，方案成立。
2. **硬杀场景**（SIGKILL、进程/系统回收页面、标签页被丢弃、渲染进程崩溃）：目标改为 **best-effort，不适用 0.1% 指标**。设计要求：
   - 把「事件产生即发送 critical（微批合并）」做成一等公民，把暴露窗口从 0–5 秒压到批量间隔量级；
   - 在 IndexedDB / OPFS 的落盘窗口验证完成之前，不承诺该场景下的丢失率；
   - 该场景必须单独计数（C08），供接收方看板区分。
3. **normal ≤ 1% 的口径边界**：仅在「页面正常离开或被隐藏」前提下适用；强杀与断网刷新下不适用（normal 不持久化，属既定取舍）。
4. **「不重复入库」仍由接收方去重保证**（RR-05 的 7 天窗口）。因离开时刻拿不到 202，**每个 critical 会被补发一次（重复 ≈ 1 倍 critical 流量）**——这是方案的确定性成本，必须写入容量估算与接收方限流评估（RR-15）。

## 备选方案与取舍

| 方案 | 优点 | 代价 |
|---|---|---|
| **分层重定目标 + 改设计**（采纳） | 目标与可达能力对齐；不把已知达不成的指标写进验收；硬杀场景仍通过「立即发送 + 单独计数」持续改进 | 需要同步修改 T16/T32/T35 的口径；硬杀场景的可靠性不再有量化承诺 |
| 不改目标，只改设计 | 保留原目标的激励作用 | 在更硬的本地持久化被验证之前，该目标在强杀场景下**已知不可达**；CI/验收会出现明知会失败的判据 |
| 只登记为已知限制，目标与设计都不动 | 改动最小 | 等于默认接受一个已知达不成的指标进入验收与发布门槛 |

## 对设计与验收的影响

- **T16（C07）**：按分层口径设计；不得以「critical 预写」作为强杀兜底；采用 POC-1 给出的推荐参数（离开预算 ≤48KB / ≤200 条 / ≤4 批；离线副本上限 5000 条、溢出先淘汰 normal；只在常规通道 202 后删副本；补发单批 ≤100、间隔 100–200 ms、单轮 ≤500 条、保留 7 天；选主用 Web Locks，BroadcastChannel 降级需 settle ≥50 ms）。
- **T32（可靠性对账）**：统计口径必须**分开**「优雅路径」与「硬杀路径」，不得合并成一个丢失率；硬杀路径只报告「暴露窗口」与「best-effort 送达率」。
- **T35（正式发布与灰度）**：发布门槛按分层口径；硬杀场景不作为发布阻断项，但必须可观测。
- **T20（性能基准）**：承接 POC-1 给出的离开预算与重复成本作为基准输入。
- **接收方**：RR-05（去重）与 RR-15（限流）从「配合项」升级为**方案成立的前提**；`receiver-requirements.md` 的容量建议需要计入「重复 ≈1 倍 critical 流量」。
