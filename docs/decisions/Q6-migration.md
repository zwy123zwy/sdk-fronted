# Q6 存量埋点迁移范围与旧链路下线

- 状态：已确认
- 确认人：wenye.zhang
- 确认日期：2026-10-09

## 问题

接入方已有埋点（自研上报或第三方 APM）时，迁移范围和旧链路的下线时间需要明确，否则新旧链路会长期并存（风险 R08）。

## 建议方案

1. **本项目的职责边界**：本项目提供迁移所需的能力和流程（双写适配器、对账报告、迁移指南），不负责改造接入方的业务代码。各接入方的迁移由该接入方负责，本项目提供陪同支持。
2. **迁移流程**（每个接入方按此执行）：
   1. 盘点现有埋点，逐条映射到埋点字典中的事件定义；
   2. 开启双写：新 SDK 正常上报，同时通过双写适配器或旧代码继续写旧链路；
   3. 用 S06 对账报告逐日比对，连续 7 天偏差不超过 1%；
   4. 关闭旧链路写入，保留旧数据只读；
   5. 观察 7 天，无异常后删除旧埋点代码。
3. **项目内的范围**：P5 的 2 个试点应用完成第 1–3 步即可满足 M6；第 4、5 步在 M8 之后的 3 个月内完成。
4. **下线期限**：每个接入方在开始双写后 3 个月内完成第 4 步。超期由项目发起人裁定是否延期。

## 备选方案与取舍

- 本项目负责改造接入方代码：迁移更快，但会让 Agent 修改接入方仓库，和指南第 0 节的约束冲突。
- 不设下线期限：接入方压力小，但旧链路会长期并存，双重成本无法收回。

## 如果结论与建议不同，需要改什么

- T19、T33 任务卡；迁移指南（T34）的范围。
- 如果改为本项目负责改造接入方代码，需要修改指南第 0、7、9 节中“不修改接入方仓库”的约束，并为每个接入方单独授权。

## 结论

采纳建议方案，并补充一条：S06 对账报告不在本项目内，改为由 SDK 提供对账所需的数据。

- C08 的 `sdk_health` 计数提供客户端一侧的发送量；
- 双写适配器（T19）提供转发计数；
- 接收方负责比对两边的入库量。

T33 试点的验收标准改为：在试点应用的预发布环境中，SDK 发送计数、双写转发计数、mock 接收服务（或试点方接收服务）入库计数三者一致，偏差不超过 1%。
