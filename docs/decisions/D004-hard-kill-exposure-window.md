- 触发：T02 追加轮（`docs/poc/POC-1-storage.md`）完成了 D003 第 2 条要求的前置验证

## 问题

D003 第 2 条把硬杀场景定为「best-effort，不适用 0.1%」，并写明「在 IndexedDB / OPFS 的落盘窗口验证完成之前，不承诺该场景下的丢失率」。该验证现已完成，证据表明这条措辞**过于悲观**：问题出在 `localStorage` 这个存储，不出在「预写」这个方案。

## 证据（POC-1 追加轮，三引擎 × 3 次独立运行，每格 1000 条样本）

`docs/poc/POC-1-storage.md`，原始数据 `poc/poc-1/results-storage-v2/`：

| 存储（落盘点定义） | Chromium | Firefox | WebKit |
|---|---|---|---|
| `localStorage`（`setItem` 返回） | Δt 0–4000 ms **存活 0/1000**，5000 ms 才 1000/1000 | Δt 0–4000 ms **0/1000**，5000 ms 仅 500–1000/1000 | Δt=0 起全部 1000/1000 |
| **`IndexedDB`（事务 `oncomplete`）** | **Δt=0 起全部 1000/1000**（3 次运行一致） | **Δt=0 起全部 1000/1000** | **Δt=0 起全部 1000/1000** |
| `OPFS`（`flush()`） | Δt=0 起全部 1000/1000 | Δt=0 起全部 1000/1000 | Δt=0 起全部 1000/1000 |
| 对照：写入被推迟（`idb-pending` / `opfs-pending`） | 0/1000 ×3 | 0/1000 ×3 | 0/1000 ×3 |

跨标签页并发写（3 标签页 × 3 轮 × 200 条 × 3 次运行）：**IndexedDB 被覆盖 0/1800**；每标签页一个文件的 OPFS 也是 0/1800；而 `localStorage` 被覆盖 600–1200/1800，「多标签页共享单个 OPFS 文件」被覆盖 600–1200/1800。

写入成本（100 条/批）：`IndexedDB` p50 1–4.1 ms、p95 3–17 ms；单条落盘 p50 1–2 ms。`durability: 'strict'` 与默认无可观测差别。

## 结论

1. **硬杀场景（SIGKILL、进程/系统回收页面、标签页被丢弃、渲染进程崩溃）不再表述为「best-effort」，改为按暴露窗口计量**：
   - **已确认落盘**（IndexedDB 事务 `oncomplete` 已返回）的 critical 事件，硬杀场景下**承诺不丢失**——三引擎实测均为 100% 存活；
   - **残余暴露窗口** = 「事件已产生但事务尚未提交」，其长度由批写提交延迟决定（实测 p50 1–4.1 ms、p95 3–17 ms），**不再是 D003 所依据的那个 0–5 秒且不确定的窗口**；
   - 该窗口内的事件必须**单独计数**并上报，供接收方看板区分（不得与优雅路径混算）。
2. **对 T16 的强制要求**：离线副本**必须使用 IndexedDB**，并以 `transaction.oncomplete` 作为唯一落盘点；**禁止用 `localStorage` 存 critical 离线副本**。若选用 OPFS，必须每标签页一个文件并把 `flush()`（而非 `close()`）作为持久点；**禁止多标签页共享同一个 OPFS 文件**。
3. **不为此引入 `durability: 'strict'`**：无可观测差别，不增加复杂度。
4. D003 第 1 条的「有优雅退出路径的场景仍适用 `critical ≤0.1%`」**不变**；D003 第 3 条（normal ≤1% 的口径边界）与第 4 条（重复 ≈1 倍 critical 流量计入容量、RR-05/RR-15 为前提）**不变**。

## 备选方案与取舍

| 方案 | 优点 | 代价 |
|---|---|---|
| **按暴露窗口计量 + 强制 IndexedDB**（采纳） | 与实测能力对齐；把「不丢」的承诺建立在可验证的落盘点上；暴露窗口可度量 | 需要 T16/T29 落实存储层与计数；任务卡口径需同步修订 |
| 维持 D003 的 best-effort 措辞 | 无需改动 | 低估了已实现的可靠性，且会让 T16 失去「用 IndexedDB」这一明确约束 |
| 恢复「硬杀也适用 ≤0.1%」 | 目标最强 | 仍不成立：暴露窗口内的事件（事件已产生但事务未提交）无法消除，用丢失率表述会误导 |

## 对设计与验收的影响

- **T16**：按第 2 条实现存储层；沿用 POC 的写入节流建议（100 条或 200 ms 取先到者）；认真对待「暴露窗口内事件单独计数」。
- **T32（可靠性对账）**：统计口径改为**三类分列**——优雅路径（按丢失率，≤0.1%）／硬杀已落盘（不丢）／暴露窗口内未提交（按条数与窗口时长计量）。**不得合并成一个丢失率。**
- **T35（发布与灰度）**：发布门槛按上述三类分列判定；暴露窗口的计数与窗口时长必须可观测。
- **T20**：承接 POC 的离开预算（≤48KB / ≤200 条 / ≤4 批）与「重复 ≈1 倍 critical 流量」作为基准输入。
- **接收方**：RR-05 去重与 RR-15 限流仍为方案成立的前提。
