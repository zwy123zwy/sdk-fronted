## 1. 最关键的一件事：装配与采集插件（T18）

> **2026-10-13 更正**：本节原写「T18 是装配根」，属**过度归属**。核对任务卡后的事实是：
> - **T18 的范围是 C05 四个采集插件**（`packages/plugins/src/{error,perf,route,http}`，卡上「文件所有权」），**不含** `packages/browser/src`；
> - **没有任何任务卡把装配根（`packages/browser` 的接线）列为所有权**——它在任务卡体系里**归属空缺**。
>   因此"把 C01–C08 装配成能端到端上报的包"这件事**需要先立项/指定归属**（建议：由负责人指定，
>   或作为 T18 的显式所有权扩展写进卡里）。下面 8 项义务本身不变，只是**归属待定**。

**装配（把各模块接起来）** 是「SDK 能否真的发出数据」的分界点。它有多项已挂账的接线义务，**缺任何一项，接入方拿到的仍是一个不会上报的库**：

2. **接 C08 的计数与计时**：把 `createQueueMetricsSource`、`createSubmitMetricsSource`、`createCallCounter`、`createLatencyDecorators` 的包装后句柄装到实际对象上；把 `createHealthReporter` 的 `emit`/`timer`/`dimensions` 接到 C01/C02/C06。**未接线前 `calls_total`/`events_enqueued`/`queue_length_max`/三个 p99 恒为 0 且不上报。**

## 4. 必须遵守的流程与口径（今天用真金白银换来的）

1. **门禁命令是 `pnpm gates`，不是 `pnpm ci`**（pnpm 11 的内置 `clean-install` 会抢占 `pnpm ci`，不跑任何门禁却返回 0）。
2. **门禁与提交分开执行**：不要把 `pnpm gates` 和 `git commit` 串在同一条命令里——门禁失败时提交照旧发生（今天因此让 main 上出现过红提交）。
3. **新工作树先 `pnpm build` 再 `pnpm gates`**（`gates` 顺序是 `lint → build → typecheck → …`，已在指南第 6 节修正；`examples/vite` 的 typecheck 需要 `packages/browser/dist`）。
4. **体积口径是 `pnpm exec size-limit`**（`import:"*"` + minify + brotli），**不要用 tsup 原样产物比**——今天就因口径混用把「超 1.32 kB」报成了「超 5.8 kB」。
5. **单元门禁不得断言微秒/毫秒级绝对墙钟目标**：只留有文档化余量的**中位数**护栏，P99/吞吐归 T20。
6. **测试先行的证据必须是断言级的**（不是 `Failed to resolve import`），并且**凡关键行为都要做变异验证**（把行为改回错的 → 用例必须变红 → 恢复）。今天的实例：T14 的第一版 AC-09 哨兵在变异下**一条都没红**（假哨兵），改完哨兵后变异才产生 6 条红；T16 的单位缺陷修复也是靠「注入旧语义 → `expected 3 to be 1`」才可信。
7. **改契约、改门禁配置、新增依赖、安全与同意相关裁定，一律先取负责人签字**（本会话用户即负责人）。
8. **先修过期文档再开工**：本会话发现 4 处任务卡的 AC 数量与验收文件不符，另有 2 处任务卡自相矛盾（T17/T25 把契约文件写进所有权范围、T13 把动作写给无权限的一方）。
