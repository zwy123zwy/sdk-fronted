## 1. 最关键的一件事：装配与采集插件（T18）

> **2026-10-13 更正**：本节原写「T18 是装配根」，属**过度归属**。核对任务卡后的事实是：
> - **T18 的范围是 C05 四个采集插件**（`packages/plugins/src/{error,perf,route,http}`，卡上「文件所有权」），**不含** `packages/browser/src`；
> - **没有任何任务卡把装配根（`packages/browser` 的接线）列为所有权**——它在任务卡体系里**归属空缺**。
>   因此"把 C01–C08 装配成能端到端上报的包"这件事**需要先立项/指定归属**（建议：由负责人指定，
>   或作为 T18 的显式所有权扩展写进卡里）。下面 8 项义务本身不变，只是**归属待定**。

**装配（把各模块接起来）** 是「SDK 能否真的发出数据」的分界点。它有多项已挂账的接线义务，**缺任何一项，接入方拿到的仍是一个不会上报的库**：

1. **调用 `captureNativeHttpRefs()`**：必须在**安装任何插件之前**、在装配根调用一次（幂等、只捕获一次、捕获后冻结）。**C05 插件不得在自己的 `install()` 里捕获**（那依赖安装顺序，太脆）。
2. **接 C08 的计数与计时**：把 `createQueueMetricsSource`、`createSubmitMetricsSource`、`createCallCounter`、`createLatencyDecorators` 的包装后句柄装到实际对象上；把 `createHealthReporter` 的 `emit`/`timer`/`dimensions` 接到 C01/C02/C06。**未接线前 `calls_total`/`events_enqueued`/`queue_length_max`/三个 p99 恒为 0 且不上报。**
3. **接 C04 的三个端口**（T14 只做了端口级验证）：`noteServerTime` → T16 的响应回调；`header()` → C06 的 `BatchHeaderSource`；`ErasePort` → C07/C03 的清理函数。

## 4. 必须遵守的流程与口径（今天用真金白银换来的）

1. **门禁命令是 `pnpm gates`，不是 `pnpm ci`**（pnpm 11 的内置 `clean-install` 会抢占 `pnpm ci`，不跑任何门禁却返回 0）。
2. **门禁与提交分开执行**：不要把 `pnpm gates` 和 `git commit` 串在同一条命令里——门禁失败时提交照旧发生（今天因此让 main 上出现过红提交）。
3. **新工作树先 `pnpm build` 再 `pnpm gates`**（`gates` 顺序是 `lint → build → typecheck → …`，已在指南第 6 节修正；`examples/vite` 的 typecheck 需要 `packages/browser/dist`）。
4. **体积口径是 `pnpm exec size-limit`**（`import:"*"` + minify + brotli），**不要用 tsup 原样产物比**——今天就因口径混用把「超 1.32 kB」报成了「超 5.8 kB」。
5. **单元门禁不得断言微秒/毫秒级绝对墙钟目标**：只留有文档化余量的**中位数**护栏，P99/吞吐归 T20。
6. **测试先行的证据必须是断言级的**（不是 `Failed to resolve import`），并且**凡关键行为都要做变异验证**（把行为改回错的 → 用例必须变红 → 恢复）。今天的实例：T14 的第一版 AC-09 哨兵在变异下**一条都没红**（假哨兵），改完哨兵后变异才产生 6 条红；T16 的单位缺陷修复也是靠「注入旧语义 → `expected 3 to be 1`」才可信。
7. **改契约、改门禁配置、新增依赖、安全与同意相关裁定，一律先取负责人签字**（本会话用户即负责人）。
8. **先修过期文档再开工**——但**判"过期"要看文件的归属/范围表述，不是数编号个数**。本会话确实发现 3 处任务卡的 AC 数量过期（T13/T14/T16），另有 2 处任务卡自相矛盾（T17/T25 把契约文件写进所有权范围、T13 把动作写给无权限的一方）。
   **但也因此踩了一个坑**：编排方只数了 `C05.md` 里的 AC 编号总数（20）就判 T18 卡"过期"，而该文件第 3 行明确写着「T18（AC-01..14、19、20）、T19（AC-15..18）」——**原卡一直是对的，是编排方的"修正"错了**，由 T18 执行方读文件时发现，已回退（`a312c47`）。**编排方的转述与编排方的"修正"都不是权威来源。**
9. **工作树基线要同步**：派工后若 main 又有契约/决策/门禁变更，**立即把 main 合入该工作树**（本会话两次因未同步让 agent 依据过期材料工作）。
10. **派工时就要要求「边写边落盘」**：subagent 在长回合中**收不到中途的 `send_message`**（本会话 T14、T18 各一次），唯一有效的干预是 `interrupt_agent`，代价是打断当前回合。T18 因此连续多轮零文件产出，被中断时它说"已经读够了、正准备写"——**工作没白费，是落盘时机错了**。所以派工提示词里就该写明：**先落盘骨架/待定项，再迭代**；并要求分多次写入而不是攒到最后一次。
10.5 **给"就地编辑既有文件"的任务放宽干预门槛——这是编排方的教训，不是执行方的。** 本会话我两次以"连续两轮无写入"中断 agent：
一次它已读完正准备写（中断后它交出了关键发现，是有效的）；另一次它正在读**它必须编辑的那个文件**
（就地编辑的前置就是先读），**那次中断是过早的**——它自己也指出了这一点。
**修正后的判断标准**：对"新建文件"类任务，两轮无写入即为异常；对"就地编辑"类任务，门槛放宽到
**3–4 轮**，且优先看它是否在**反复读同一批文件**（真卡住的信号），而不是单看有没有写入。
10.6 **排查 flaky / 性能波动前，先确认机器空闲**（本会话的实战教训）：本会话有 **4 条**用例被怀疑是抖动——排查后真相是 **1 条 O(n²) 实现缺陷 + 1 条"运气型"间歇失败（命中率≈0.06%）+ 2 条真·重负载敏感**。做法：
  ① 先用 `node -e "console.log(require('os').loadavg())"` + `pgrep -lf node` 确认无 vitest/tsc/build/浏览器（`ps`/`top` 可能被沙箱拒）；
  ② 空闲复现不出时，**用"两个并发 vitest 进程"构造受控负载**复现——这模拟的正是"门禁与重任务并行"的真实条件；
  ③ **长期留存门禁日志**：本会话那条"运气型"失败的根因，就是靠**从留存的 `/tmp/gates-*.log` 里找回报错原文**
     （`instancePath: /events/0/view_id`）才定位的——**看板上只写"曾红"是不够的**。
  ④ **门禁不应与重任务并行跑**：负载下另有两条重负载敏感用例偶发红（`C05-AC-18 gzip`、`mask-adversarial` perf 护栏），空闲全绿。

11. **不要留未跟踪文件**：K02 的泄漏扫描有一条「零新增未跟踪文件」断言，会把它们判成红（今天误伤过一次）。
