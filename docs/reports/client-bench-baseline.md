## 3. 体积（gzip）

方法与边界：

1. **加载桩**：`packages/browser/src/loading-stub.ts` 用仓库自带 tsup（esbuild）打成压缩 IIFE
   （输出到 `tests/bench/.tmp/`，用完即删），再 gzip(level 9)：**733 B ≤ 1 KB**（brotli 640 B）。
2. **各包产物**：**按 `size-limit` 的 `import: "*"` 口径复现**——对 `.size-limit.json` 里声明的同一个
   路径做一次 esbuild 打包 + minify，再 gzip。直接压未压缩的 `dist/index.js` 会得到完全不同量级
   （例如 core 文件本身 gzip 31866 B），**不能**与门禁预算比较——本任务第一版脚本正是这么错的，已修正。
3. **不重建任何包**：只读磁盘上已有的 `dist/`。报告同时给出「本包产物是否比源码旧」。
   本次 **core 的产物被判定为比源码旧**（`packages/core/src` 有文件新于 `packages/core/dist/index.js`），
   因此 core 的 21146 B / 21 KB（余量仅 1.02×）**需要在重新构建后再确认**。
4. `.size-limit.json` 属另一 agent 的所有权范围，本任务**只读不写**，也未运行 `pnpm size`。

| 对象 | 现行预算（2026-10-13 批准） | 实测 gzip | 余量 | 判定 |
|---|---|---|---|---|
| 加载桩（压缩 IIFE） | 1 KB（T12） | 733 B | 1.40× | 达标 |
| core | 21 KB | 21146 B | 1.02× | 达标（**余量仅 2%**，且产物可能过期） |
| transport | 18 KB | 17191 B | 1.07× | 达标（余量 7%） |
| plugins | 20 KB | 6838 B | 3.00× | 达标 |
| browser | 13 KB | 39728 B | 0.34× | **不达标，但本行不作为结论** |
| `<script>` 全量 IIFE | 无独立目标 | 39986 B（brotli 35354 B） | — | 仅记录 |

**关于 browser 的 39728 B**：`packages/browser/dist/index.js` 目前是 core 全导出面的 re-export 壳，
按 `import: "*"` 口径打包会把整个 core 内联进来，必然是 core 量级。`.size-limit.json` 自己的条目名
已写明「⚠ 装配根 T18 落地后应改量实际发货的 bundle」，而 T18 正在改动中（本任务被要求**不碰
`packages/browser`**）。因此这一行**标记为口径未定**，需要在 T18 落地、预算表重新推导后再测，
**不得**据此判定不达标（否则等于用旧口径的产物给新入口定罪）。

## 4. 与历史值的对比（② 趋势对比）与可复现性

**均只报告，不做门禁。**

- **重复性目标「波动 ≤ 5%（T20.md 非功能目标）」在本机共享环境下未达成**：同机另有 agent 在编译/跑门禁
  （`load average 4.5–5.5`），3 次运行中总有一次整体抬高 2–5 倍（例如 C01 push 组耗时 P50 从 0.0063 ms
  涨到 0.0098 ms；C04 处理器 P99 从 0.031 ms 涨到 0.061 ms）。
- **确定性行波动 0.00%**：字节数、流量占比、条数类指标（C02/C06 内存、C08 两个占比）在 3 次运行中完全一致
  ——这些是可以在 CI 里当硬数字用的。
- **P50 时间行**：多数 ≤ 5%（如 C06 组装+序列化 5.9%、C01 吞吐 2.8%）；受污染的那一轮可到 38–52%。
- **P99/P95 时间行**：在**亚微秒**量级上，本机 `performance.now()` 的粒度约 **41.7 ns**（实测值都是
  0.0000417 的倍数），因此 P99 的相对波动被**计时器量化**主导（如 0.000125 vs 0.000167 = 3 跳 vs 4 跳），
  绝对抖动只有 ~42 ns（占契约预算的 0.4%）。**解释方差时必须同时给绝对值**，否则会误报「不稳定」。
- **堆增量行不可复现**：`heapUsed` 增量在 3 次运行中出现过一次 **−8 MB**（测量期间发生 GC），
  因此内存判定一律用确定性字节口径，堆增量只作上界参考（已在 `tests/bench/README.md` 写明红线）。
- 结论：**「CI 可复现」需要一个安静的专用 runner**。本机数字只能用于达标判定与容量估算，
  不能用于秒级以下的趋势门禁。

## 6. 不达标项与升级（T20.md 要求：列出并升级前端负责人，**不得**调整测量方法以「达标」）

### 6.1 C04 富化与脱敏 P99 ≤ 0.03 ms —— **未达标**（核心缺口）

- **实测**（3 次运行，n=20000）：字段约束 + 脱敏处理器 **P99 = 0.0312 / 0.0370 / 0.0610 ms**
  （P50 0.0265 / 0.0277 / 0.0315 ms）；契约目标 0.03 ms → **P99 中位数超 23%**。
- 脱敏器**单独**处理 256 字符（C04 允许的单值上限）**P50 就已 0.0313–0.0374 ms、P99 0.0372–0.0418 ms**，
  **三次运行的 P50 全部超过 0.03 ms** → 这是一个稳定复现的缺口，不是离群值。
- **根因（本基准额外测出的成本曲线，`c04-privacy.bench.ts`）**：脱敏器成本随字符串长度**超线性**增长：

  | 字符串长度 | apply() P50 | 每字符 |
  |---|---|---|
  | 32 字符 | 0.00125 ms | 39 ns |
  | 64 字符 | 0.00517 ms | 81 ns |
  | 128 字符 | 0.01588 ms | 124 ns |
  | 256 字符 | 0.03446 ms | 135 ns |

  长度 ×8（32→256）而耗时 ×27.6 → 约 O(n^1.6)，**不是**线性扫描的正常表现。按 P99 计，
  0.03 ms 的预算只够处理 **≲ 200 字符**的受脱敏文本；而 `MAX_DIMENSION_VALUE_LENGTH = 256`
  允许单值 256 字符，且一条事件的每个字符串值都要过脱敏器。
- **建议**（不在本任务可写范围内，交前端负责人）：把脱敏器改成单趟扫描（所有规则一次遍历、
  命中即跳过后续规则），或对纯 ASCII 无敏感片段做快速路径；改完用本基准复测 32/64/128/256 四点。
- 备注：单元护栏（`packages/core/src/privacy/perf.test.ts`，中位数护栏 0.5 ms）**拦不到**这个缺口，
  因为 0.03 ms 的目标是被它有意让位给 T20 的。参考：把 `makeEvent()` 也算进计时区的「对照行」
  P99 为 0.032–0.036 ms，与单元护栏注释里「全量并行下中位数 0.074 ms」一致量级。

### 6.2 C02 预启动队列内存 ≤ 256 KB / 500 条 —— **在「生产上界形态」事件下未达标**

- **实测**：500 条事件的体积（仓库口径 = JSON 码元数，与 `event-standard.md` 第 4 节一致）
  - 典型形态（3 个短维度、无长值）：**110 KB**（226 B/条）→ 达标；
  - 生产上界形态（含 200 字符长值 + 一处伪造 PII）：**317 KB**（650 B/条）→ **超预算 24%**；
    内存保守上界（UTF-16×2）556 KB。
- **这是容量口径问题，不是实现缺陷**：256 KB / 500 条 **隐含平均 ≤ 524 B/条**；而 C04 允许
  单个字符串值到 256 字符（`MAX_DIMENSION_VALUE_LENGTH`，即单值 512 B）。也就是说
  **一条事件只要带一个接近上限的长值，就已经吃掉整条均值预算**，第二个字段起必然超。
- **建议**：要么把预启动队列的预算与队列条数解耦（按字节配额，超配额淘汰最早的 normal，
  与 C06 的 `QUEUE_MAX_BYTES = 512 KB` 同构），要么在文档/预算表里写明「预启动队列的 256 KB
  仅对平均 ≤ 524 B 的事件成立」。**不要**通过把长值事件从夹具里拿掉来「达标」。

### 6.3 体积：browser（口径未定）与 core（余量 2%）

- `browser` 的 39728 B > 13 KB：**不据此判定**，原因见 §3（T18 进行中、口径待重定）。
- `core` 的 21146 B / 21 KB（**余量 1.02%**）：即使按现有预算也只剩 358 B 余量；且本次测量用的
  `dist` 被判定为**比源码旧**。这一条应在 T18 落地、预算表重新推导后重测——**当前处于随时会突破的
  临界状态**，建议在预算表重推时把 core 的余量目标写进门禁口径。

### 6.4 已达标但有价值的高水位项

- **C06 入队 P99 余量仅 3.6–3.9×**（0.0026–0.0028 ms vs 0.01 ms）：是时间指标里最紧的一个，
  值得进 CI 持续观察。
- **C07 100 条批次 `prewrite` 余量 10.5×**：同步路径当前不做整批序列化，容量再放大前需注意。
