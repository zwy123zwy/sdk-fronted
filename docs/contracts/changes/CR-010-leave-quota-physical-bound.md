# CR-010：离页信标通道的**累计额度**是物理约束——修订 C07-AC-03 的口径

- **状态**：已批准（2026-10-15，编排方按负责人"全部同意，按你的方案来"的授权签署；**待安全/前端负责人追认**）
- **类型**：**0.2 兼容澄清**（不新增字段、不改字段语义、不升版本号）

## 背景：一次实测发现验收口径与浏览器能力冲突

`tests/acceptance/C07.md:9` 的 **C07-AC-03** 原文要求：
「页面离开时冲刷 80 KB 数据 → 使用信标通道，**拆成至少两个不超过 60 KB 的请求**；`Content-Type` 为 `text/plain`；令牌在 `auth` 字段。」

**真实 Chromium 与 WebKit 的实测（`docs/reports/e2e-real-browser.md` 追加节，两次独立运行逐位一致）**：
- 浏览器**除单次上限外还有「同一同步回合的累计在途额度」，实测恰为 `65536 B`**（`[32K]→true`、`[32K+32K]→[true,true]`、**累加超 65536 即拒**，拒绝点 73728）；
- **该额度不因"让出到新任务"而重置**：本回合同步写 `64686 B` 被接受后，让出到 `setTimeout(0)` 的**第 3 片仅 `19695 B`（≪65536 B）仍被拒**
  （`64686+19695=84381 > 65536`，由数字反推）；**放宽预算到 4 MB 数字一字不变** ⇒ 与预算无关；
- 因此 **80 KB 载荷在一次离页内物理上无法全送达**（上限 ≈64 KiB）。

## 本 CR 固定的事实与要求（**不改变"必须尽力送达"的精神，只写清物理边界**）

1. **`60 KB`/片的单请求上限继续有效**（这是契约约束，SDK 与接收方都依赖它）；
2. **新增物理约束**：**同一同步回合的累计写入量**受浏览器额度限制（实测 `65536 B`，**不同引擎/版本可能不同**），
   SDK **必须按回合约束写入量**，**不得**依赖"让出到新任务"来重置额度（**已实测不成立**）；
3. **超出可送达能力的部分必须可见**：`leave.stats.skipped` **必须等于未送达的事件数**，
   且 **`sent + skipped = 提交总数`**、**`sent` 不得超过接收端重组到的条数**；
   **禁止**"自报 `sent` 全量而实际丢条"（这正是本次修复前发生的事）；
4. **`flush_skipped_due_to_budget` 的触发条件扩容**（已在本 CR 前由 CR-009 澄清）：除字节/条数/批数/时间窗外，
   **包含"浏览器同回合累计额度导致的整片拒绝"**。

## 对验收口径的影响

**C07-AC-03 的"80 KB 全部送达"不可判定为通过**（物理不可达）。建议改为：

> 「页面离开时冲刷 80 KB 数据 → 使用信标通道，**拆成至少两个不超过 60 KB 的请求**；
> **在浏览器同一同步回合的累计额度内尽可能送达**；**未能送达的部分必须计入 `leave.stats.skipped` 并可对账**
> （`sent + skipped = 提交总数`，且 `sent` = 接收端实际重组到的条数）；`Content-Type` 为 `text/plain`；令牌在 `auth` 字段。」
