# 接收方要求

- 版本：0.2（已冻结，2026-10-10；批准见 `README.md`“冻结记录”）
- 对应任务：T05；依据：`docs/decisions/D001-scope.md`
- 适用对象：在生产环境接收本 SDK 上报数据的服务（由接入方或其他团队提供）。本项目的 M01 mock 接收服务（T09）实现全部“必须”条目，只用于测试。

本 SDK 只负责客户端一侧。critical 事件“丢失率不超过 0.1%”和“不重复入库”的端到端目标，只有在接收方满足本文“必须”条目时才成立。接收方按本文自查；本项目不验证接收方的实现。

## 1. 协议

| 编号 | 要求 | 级别 | SDK 依赖的原因 |
|---|---|---|---|
| RR-01 | 实现 `ingest-protocol.md` 第 1–3 节的端点、请求格式、上限与响应码 | 必须 | C07 按响应码决定重试、拆分、丢弃 |
| RR-02 | 只在批次已持久化（写入队列或存储）之后返回 202；任何失败都不得返回 2xx | 必须 | SDK 收到 202 后删除 critical 离线副本，提前返回会造成丢失 |

| RR-04 | 支持 `Content-Encoding: gzip`；流式解压，解压量达到 1 MB 立即中止并返回 413（防 gzip 炸弹）；压缩后超过 256 KB 直接返回 413；其他编码返回 400 | 必须 | C07-F8 压缩 |
| RR-05 | 按 `app_id` + `event_id` 在至少 7 天窗口内去重 | 必须 | SDK 为保证不丢失会重复送达（重试、补发、多标签页），去重由接收方完成 |
| RR-06 | 按 `event-standard.md` 的提升规则还原批次 `common` 字段；事件体中的值优先 | 必须 | SDK 会把公共字段提升到 `common` 以减小体积 |
| RR-07 | 429、503 返回 `Retry-After`；所有响应返回 `X-Server-Time` | 应该 | 退避与时钟校准（C04-F7） |
| RR-08 | 支持 CORS：允许 SDK 所在页面的来源、`POST`、`Content-Type`、`Content-Encoding`、`X-App-Id`、`X-Write-Token`、`X-Request-Id`；暴露 `Retry-After`、`X-Server-Time` | 必须 | 跨域上报 |

## 4. 容量建议（不作为本项目验收标准）

依据 Q1 的参考值：首年日活设备 50 万，日均 5,000 万条事件，峰值 2 万条/秒，平均每批 15 条（约 1,500 个请求/秒），建议按 3 倍余量规划。SDK 单页面峰值约每秒 30 条事件。

**必须计入重复流量（≈ 1 倍 critical 流量）**：critical 事件在页面离开时刻**拿不到 202**，因此会在下次进入时被**补发一次**（见 `docs/decisions/D003-critical-reliability-tiered-target.md` 第 4 条）。这是方案的**确定性成本**，不是异常：容量估算与限流评估都必须在 critical 的实际流量之外**再加一份**。

由此，RR-05（去重，7 天窗口）与 RR-15（限流）**不是可选的配合项，而是方案成立的前提**：接收方若不做去重，critical 的入库计数会翻倍；若不做限流，离开时刻的集中补发会与正常流量叠加。

## 4.1 容量估算示例

| 项 | 取值 |
|---|---|
| 业务事件（normal） | Q1 参考值（日均 5,000 万条） |
| critical 事件 | 按实际配置的 critical 事件定义统计（指南的字典里以 `critical` 标记） |
| **critical 重复流量** | **≈ 1 × critical**（离开时刻补发一次） |
| 规划余量 | 上述合计的 3 倍 |

**不得把 critical 与其重复流量合并成一个数**去比对门槛：重复是确定性的补发，与「事件是否真的产生过」是两回事；接收方看板应能分别看到「去重前的收到量」与「去重后的入库量」。

## 附录 A：`sdk_health` 字段

（2026-10-13 由 CR-002 补全；T17/C08 已交付）

子章节编号 A.1–A.6 为 2026-10-13 经 CR-002 追加，属兼容变更（不递增文档版本号）。

### A.1 事件形态

`sdk_health` 是普通上报事件：走同一条批次通道、同一个 `app_id`+`event_id` 去重键（RR-04、RR-05 同样适用）。顶层含 `event_id`、`event_name`（`sdk_health`）、`event_type`（`sdk_internal`）、`schema_version`、`occurred_at`、`priority`（固定 `normal`，Q3 结论第 4 条）、`dimensions`、`metrics`。

**字段的权威定义是机器可读的 [`schemas/builtin-events/sdk_health.schema.json`](schemas/builtin-events/sdk_health.schema.json)**；本附录**不复制字段表**，以免与 Schema 漂移。接收方建看板应以该 Schema 为准，并可用 [`examples/builtin-events/sdk_health.valid.json`](examples/builtin-events/sdk_health.valid.json) 做实现自测。字段含义见 `reason-codes.md` 第 4 节。

### A.2 `dimensions`

`sdk_version`（semver，产生本窗口数据的 SDK 版本）、`state`（`initialized`｜`running`｜`paused`｜`destroyed`；SDK 的「未初始化」态不上报）、`config_version`（十进制字符串；无生效配置时省略）。

### A.3 `metrics` 的读数口径（接收方最容易读错的地方）

1. **计数类指标值为 0 时不上报。** 因此「某个 `drop_*` / `count_*` 键不出现」等价于「该窗口内为 0」，**不要当成缺数据或上报失败**。
2. **`offline_written` / `offline_replayed` 的单位是「批次数」，不是事件数**（事件数另有本地观测量，不进契约指标）。接收方按批次数建看板。
3. **`exposure_window_ms` 必须与 `exposure_window_events` 同时出现**（Schema 的 `dependentRequired`，机器可校验）；`exposure_window_events` 为 0 时两者都不上报。
4. **`batches_sent` 与 `batches_failed` 不互补。** 前者只计常规通道成功提交的批次；后者含熔断（`circuit_open`，未尝试发送）与终态 4xx 拒绝；两者都**不含**离开通道与补发批次（补发计 `offline_replayed`，避免同一批次被两个指标各记一次）。**不要用 `sent + failed` 反推提交总数。**
5. **`queue_length_max` 是窗口内的队列长度峰值**，在非自监控事件的入队时刻采样。
6. 三个 `*_p99_ms` **只在 1% 会话上报**（见 `sample_rate`）。

### A.4 上报节奏与分片

窗口常规为 60 秒（`window_ms`）。**一个窗口内非零指标超过 50 个时，SDK 会拆成多条 `sdk_health`**（Schema 的 `maxProperties: 50`），每条带**相同的 `window_ms` 与 `dimensions`**、各自的 `event_id`。

**接收方聚合时必须把「同 `window_ms` + 同 `dimensions`」的多条事件视为同一窗口**，否则会把一个窗口拆成多行、把计数当成多份。

### A.5 流量占比

自监控流量占业务流量的实测口径与结果（T17，确定性计数）：1 条 `sdk_health`（12 个指标、约 480 B）对 1000 条业务事件（约 467,000 B）→ **计数比 0.100%、体积比 0.1028%**（均 ≤1%，符合 C08 的非功能目标）。接收方按此估算容量。

### A.6 调试模式

调试模式是**纯本地输出**（接入方控制台或 logger），**不产生额外的上报事件**，因此不改变接收方侧的数据形态。
