# 上报协议 I-01

- 版本：0.2（已冻结，2026-10-10；批准见 `README.md`“冻结记录”）
- 对应任务：T05；需求：C07-F1、C07-F2、C07-F3、C07-F4、C07-F8；接收方要求 RR-01 至 RR-08
- 提供方：接收方（不在本项目内，见 D001；本项目的 M01 用于测试）；调用方：C07 传输模块
- 本协议作为对外规范发布。冻结后的修改需要与已知接收方协商，并按 `README.md` 的版本规则执行。

## 1. 端点

| 项 | 值 |
|---|---|
| 方法 | `POST` |
| 路径 | `/v1/batch`；主版本号体现在路径中 |
| 协议 | 必须是 HTTPS（TLS 1.2 及以上）。M01 只监听 `127.0.0.1`，例外使用 HTTP |
| 端点来源 | 初始化参数 `endpoint`，远程配置 `endpoints.ingest` 可以覆盖；SDK 不得内置默认域名 |

## 2. 请求

### 2.1 常规通道（fetch keepalive 或 XMLHttpRequest）

| 请求头 | 必填 | 说明 |
|---|---|---|
| `Content-Type` | 是 | `application/json` |
| `Content-Encoding` | 否 | 压缩时为 `gzip`。只有批次序列化后超过 4 KB、且浏览器支持 `CompressionStream` 时才压缩（C07-F8）。SDK 不发送其他编码 |
| `X-App-Id` | 是 | 应用标识，必须与请求体中的 `app_id` 一致 |
| `X-Write-Token` | 是 | 只写令牌 |
| `X-Request-Id` | 否 | 与请求体 `batch_id` 相同，便于接收方日志关联 |

请求体为一个批次，结构见 `schemas/batch.schema.json`。

### 2.2 信标通道（页面离开时）

`navigator.sendBeacon` 不能设置自定义请求头，也不能设置 `Content-Encoding`。因此：

- 请求体不压缩，`Content-Type` 为 `text/plain;charset=UTF-8`，内容为批次 JSON。使用 `text/plain` 是为了避免触发跨域预检。
- 令牌放在请求体的 `auth.write_token` 字段，`auth.app_id` 与批次的 `app_id` 一致。**令牌不得放在 URL 中。**
- 请求体不得超过 60 KB（C07-F1 预先切片的上限），超过时由 C07 拆分成多个信标请求。
- 接收方通过 `Content-Type` 识别信标通道，从请求体读取令牌；常规通道的请求体中出现 `auth` 字段时，接收方必须忽略它，只认请求头（RR-03）。
- 接收方不得在任何日志中记录 `auth` 字段（RR-13）。

令牌位置已由 R-001 确认（见 `docs/review-log.md`）：放在请求体满足“令牌不进入 URL 与访问日志”的要求。

### 2.3 限制

| 项 | 上限 | 超限时 |
|---|---|---|
| 请求体（解压后） | 1 MB | 413 |
| 请求体（压缩后，常规通道） | 256 KB | 413 |
| 单批事件数 | 500 | 413 |
| 单条事件序列化后 | 16 KB | SDK 侧保证（C04-F6）；接收方可以只拒绝该条，其余事件正常处理 |

SDK 自身的批次上限远小于以上数值（`max_batch_events` 不超过 100，`max_batch_bytes` 不超过 60 KB），这些上限是接收方的防护边界。解压时的资源控制见 `receiver-requirements.md` RR-04。

## 3. 响应

### 3.1 响应码

| 响应码 | 含义 | 客户端行为 | 原因码（C08 计数） |
|---|---|---|---|
| 202 | 批次已持久化 | 视为成功，删除离线副本 | — |
| 400 | 批次结构非法、协议版本不支持、`app_id` 不一致 | 丢弃并计数，不重试 | `rejected_400` |
| 401 | 令牌无效或已吊销 | 丢弃并计数；暂停发送，直到下一次配置拉取成功并且令牌或端点发生变化 | `rejected_401` |
| 403 | 来源域名不在白名单、应用被停用 | 同 401 | `rejected_403` |
| 413 | 请求体或事件数超限 | 拆成两半重发，计数 `split_413`；单条事件仍然超限时丢弃该条 | `rejected_413` |
| 429 | 限流 | 按 `Retry-After` 退避重试 | `retry_429` |
| 5xx | 服务暂时不可用 | 指数退避重试，超过次数后落盘待补发 | `retry_5xx` |
| 网络错误、超时 | — | 同 5xx | `retry_network` |

其他未列出的 2xx 按 202 处理，其他 4xx 按 400 处理。信标通道无法读取响应：`sendBeacon` 返回 `true` 只表示浏览器接受了请求，C07 对 critical 批次不得因此删除离线副本，等下一次常规通道的补发确认（C07-F5）。

**接收方必须只在批次持久化之后才返回 202**（RR-02）。任何失败都不能返回 2xx。

### 3.2 响应头

| 响应头 | 出现条件 | 说明 |
|---|---|---|
| `Retry-After` | 429、503 | 秒数，整数。客户端取它与本地退避时间中的较大值，上限 60 秒 |
| `X-Server-Time` | 所有响应 | 接收方当前 UTC 毫秒时间戳，用于时钟校准（C04-F7） |
| `X-Request-Id` | 所有响应 | 回显请求的 `X-Request-Id`；请求中没有时由接收方生成 |

`Retry-After`、`X-Server-Time` 缺失或格式非法时，客户端按没有该响应头处理，不得报错。

### 3.3 响应体

202 时响应体可以为空。4xx 和 5xx 时为：

```json
{ "error": "payload_too_large", "message": "batch exceeds 500 events" }
```

`error` 的建议取值见 `reason-codes.md` 第 3 节。客户端只按响应码决定行为，不得依赖 `error` 和 `message`；调试模式下可以把 `error` 显示出来。

## 4. 重试与幂等

- 客户端重试时必须保持 `batch_id` 和每条事件的 `event_id` 不变；拆分重发时生成新的 `batch_id`，`event_id` 不变。
- 接收方按“`app_id` + `event_id`”在至少 7 天窗口内去重（RR-05），所以同一事件重复送达不会重复入库。
- 退避：首次 1 秒，倍数 2，上限 60 秒，最多 3 次，带 ±20% 的随机抖动（C07-F3）。
- 熔断：连续 5 个批次失败后暂停发送 5 分钟，只入队不发送，计数 `circuit_open`，之后放行一个探测批次（C07-F4）。401、403 不计入熔断，走暂停逻辑。

## 5. 已关闭的评审问题

| 问题 | 结论 |
|---|---|
| 信标通道的令牌位置 | 放在请求体 `auth` 字段，见 R-001 |
| 压缩后 256 KB 上限与解压资源占用 | 接收方的实现问题，写入 `receiver-requirements.md` RR-04；POC-2 随 D001 取消 |
| 是否支持 `deflate`、`br` | 不支持。SDK 只发送 `gzip`；接收方收到其他编码时返回 400 |
| 网关附加信息（原 I-03） | 属于接收方内部实现，移出本协议，见 `receiver-requirements.md` RR-13 对 IP 与令牌的约束 |
