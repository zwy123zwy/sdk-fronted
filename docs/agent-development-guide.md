# Web 自定义上报 SDK：AI Agent 开发指南

本指南面向在 SDK 仓库中执行任务的 AI Agent（A00–A14）及其对接的人类负责人，规定 Agent 开工前读什么、在哪里写代码、按什么流程交付、遇到什么情况必须停下。

总体设计见飞书文档《Web 自定义上报 SDK 系统设计方案》：
https://nwd4iy9rd2s.feishu.cn/docx/D9wXdUn8xooIu8x9RVDchSeanDg
文中的模块编号（C01–C08）、需求编号（如 C07-F3）、任务编号（T01–T37）、角色编号（A00–A14）与本指南一致。总体方案中的 S01–S07 不在本项目范围（D001），只作为接收方要求的来源。

## 0. 仓库定位

- SDK 是独立项目，使用 TypeScript 编写，编译产物为 JavaScript 包。接入方以 npm 依赖的方式引用它，不复制源码。
- 范围以 `docs/decisions/D001-scope.md` 为准：**只做浏览器 SDK**（C01–C08），另加三个开发与测试工具，都放在本仓库 `tools/` 下：
  - K01 事件注册表与类型生成 CLI（T22）
  - K02 配置签名 CLI（T25）
  - M01 本地 mock 接收服务（T09），只用于测试，不得用于生产
- 接收服务、处理管道、存储、看板、控制台不在本项目内。生产接收方需要满足 `docs/contracts/receiver-requirements.md`。
- Agent 只在本仓库写代码，不修改任何接入方的仓库。

## 1. 信息优先级

多份材料说法冲突时，按以下顺序取用，并在交付报告中写明冲突点：

1. `docs/contracts/` 下已冻结的契约文件
2. 本任务的任务卡 `docs/tasks/Txx.md`
3. 本指南
4. 飞书总体设计方案
5. 本仓库已有代码的写法

契约与任务卡存在歧义或互相矛盾时，不要自行选择一种理解继续开发，按第 7 节升级。

## 2. 每次开工的必读范围

不要一次读入整份总体设计方案。每个任务只读以下内容：

- 本指南第 0–8 节
- 本指南第 9 节中自己角色的条目
- 任务卡及其“上下文切片”列出的方案章节（第 12 节给出默认切片）
- 任务卡引用的契约文件
- 任务卡“文件所有权”范围内的现有代码

读完后在实施计划中列出“已读清单”。需要超出切片的信息时，可以读取，但要在计划里写明原因。

## 3. 仓库与目录约定

技术栈：TypeScript（strict 模式）、pnpm workspace、tsup 或 Rollup 打包、Vitest 单元测试、Playwright 做 E2E 和兼容性测试。T08 冻结具体版本。

产物要求：

- 输出 ESM 包，编译目标默认 ES2020，T08 根据目标浏览器矩阵确认。必要时再额外输出 IIFE 版本，供非构建环境通过 `<script>` 引入。
- 每个包都要发布 `.d.ts` 类型声明。
- 运行时依赖为零。核心包不依赖任何框架；框架集成（如 Vue、React 的错误处理接入）各自放在单独的包里，框架声明为 peerDependency。

## 4. 接入方式与兼容要求

### 4.1 分发方式

| 阶段 | 方式 | 说明 |
|---|---|---|
| 本地联调 | 接入方通过 `pnpm add <包名>@link:<SDK 仓库路径>/packages/browser` 引用 | 只在本地使用，不提交到接入方仓库 |
| 测试与预发布 | 发布带 `-beta.N` 后缀的预发布版本到私有源 | 接入方锁定精确版本 |
| 正式使用 | 发布正式版本，遵循 semver | 接入方锁定精确版本 |

### 4.2 兼容要求

- 在主流构建工具（Vite、webpack）的生产构建、开发服务器，以及 Vitest、Jest 测试环境中，SDK 都必须能直接导入，不需要额外配置。T08 在 `examples/` 中至少提供一个 Vite 示例和一个 `<script>` 引入示例，验证这一点。
- SDK 不假设接入方使用某个 HTTP 库、状态管理库或第三方 APM。需要和它们交互时（比如双写适配器），通过注入接口实现，不直接 import。
- 公共 API 有任何变化，都要同步更新类型声明和 `CHANGELOG.md`。破坏性变更只能出现在主版本中。

### 4.3 API 设计用例

A03 设计 C05 插件和公共 API 之前，先在 `docs/use-cases.md` 中列出典型上报场景，并逐条确认它们都能用 SDK API 表达出来。至少覆盖以下场景：

- 错误、性能、HTTP 请求的自动采集，并支持按规则过滤
- 登录后设置用户，退出后清除
- 页面内的业务操作轨迹（高频事件，会话结束时需要可靠送达）
- 媒体播放类指标（播放、拖动、卡顿）
- 远程配置下发后，动态调整采样和开关
- 与已有第三方 APM 并行运行的双写阶段

从已有系统迁移到 SDK 时，按先双写、再对账、最后切换的顺序进行。

## 5. 单任务工作流程

1. **领取**：只领取 A00 已发布、依赖全部验收的任务卡。任务卡缺任何必填字段（见第 10 节）时退回 A00。
2. **准备工作区**：在独立分支上开发，分支名为 `Txx-简短描述`；同一时间一个分支只做一个任务。
3. **阅读**：按第 2 节读取上下文。
4. **提交实施计划**：包括已读清单、要改的文件、实现要点、风险、对契约的疑问。高风险任务（C07、K02、所有安全相关任务）和存在契约疑问的任务，必须等对接负责人确认计划后才能动手。
5. **先跑验收用例**：确认 A09 编写的验收用例存在，并且在当前状态下失败。执行 Agent 不得修改验收用例，觉得用例有误时按第 7 节升级。
6. **实现**：只改文件所有权范围内的文件。可以补充自己的单元测试。
7. **本地自检**：运行第 6 节的全部门禁，全部通过后才提交。
8. **提交合入请求**：使用第 8 节的交付报告模板。
9. **评审循环**：依次经过 CI 门禁、A12 AI 评审（安全相关任务加 A11 扫描）、人类负责人评审。任一环节未通过就回到第 6 步。同一门禁连续 2 次未通过时，停止并升级。
10. **收尾**：人类负责人合入后，A09 跑回归，A00 更新看板并解锁下游任务。执行 Agent 要确认交接产物（已发布的包版本、契约样例）已经可用。

## 6. 本地门禁命令

命令名由 T08 冻结（2026-10-10），定义在根目录 `package.json`。CI 配置为 `.github/workflows/ci.yml`。

2026-10-12 修订（第 0.6 版）：全量门禁脚本由 `ci` 改名为 **`gates`**。原因是 pnpm 11 的内置 `clean-install` 会抢占 `pnpm ci` 这个名字——它只做干净安装、不执行任何门禁，却返回退出码 0，会让 Agent 误判门禁已通过。CI 工作流逐条调用门禁命令，不受影响。

| 命令 | 检查内容 |
|---|---|
| `pnpm lint` | ESLint（typescript-eslint strict type-checked）；禁止 `any`、未处理的 Promise、`class`、`@ts-ignore`、`.skip`、`.only`；`noInlineConfig` 使 `eslint-disable` 注释无效 |
| `pnpm typecheck` | `tsc`，所有包开启 strict、`noUncheckedIndexedAccess`、`exactOptionalPropertyTypes` |
| `pnpm test` | Vitest 单元测试（happy-dom）与覆盖率；`packages/core`、`packages/transport` 行覆盖率不低于 90%，`packages/plugins` 与 `tools/` 不低于 80% |
| `pnpm build` | 构建所有包，产出 ESM、类型声明，以及 browser 包的 IIFE |
| `pnpm size` | 体积预算（口径为 size-limit 的 `import: "*"` + minify + brotli，**不要用 tsup 原样产物比**）；browser 入口与 core 不超过 10 KB，**transport 不超过 18 KB**（2026-10-13 经负责人批准分两步由 10 KB 提高：C07 落地后实测 11.32 kB → 15 KB；C08 落地后实测 14.82 kB → 18 KB），plugins 全量不超过 20 KB，超出时阻断。**硬约束**：C07+C08 装配进浏览器包时必须**重新推导整张预算表**（含 `browser` 的 10 KB）——现有额度是在 C07/C08 存在之前定的，**逐次抬高不是长久办法**（触发条件见 `docs/tasks/board.md`） |
| `pnpm api:check` | API Extractor 公共 API 审计，与各包 `etc/*.api.md` 比对；有未登记的变更时阻断。有意变更时运行 `pnpm api:update` 并在合入请求中说明 |
| `pnpm test:contract` | 契约测试；T10 已补齐双向校验：既检查 Schema 版本与样例合法性，也校验 SDK 真实产出（`tests/contract/sdk-core-output.test.ts`、`sdk-batch-output.test.ts`） |
| `pnpm examples:build`、`pnpm examples:test` | 接入兼容性：Vite 构建、`<script>` 引入 IIFE、Vitest 与 Jest 中直接导入 |
| `pnpm test:e2e` | Playwright（Chromium、Firefox、WebKit）；在 CI 中运行，本地可选 |
| `pnpm gates:selftest` | 门禁自检：逐个注入违规样例，确认 lint、typecheck、size、api:check 都会失败 |
| `pnpm gates` | 按 CI 顺序运行除 E2E 之外的全部门禁：`lint → build → typecheck → test → size → api:check → examples:build → examples:test`。**`build` 必须先于 `typecheck`**：`examples/vite` 的 typecheck 需要解析 `@web-report-sdk/browser` 的 `dist` 类型，新工作树或新克隆若先跑 typecheck 会以 `TS2307` 失败（2026-10-13 修正）。**不得使用 `pnpm ci`**：pnpm 11 的内置 `clean-install` 会抢占该名字，它只做干净安装、不执行任何门禁，却返回退出码 0 |

门禁失败时修复代码，不要通过修改门禁配置、跳过测试、添加 `--no-verify`、`eslint-disable`、`@ts-ignore`、`it.skip` 等方式绕过。如果确实需要豁免，在交付报告中说明，由人类负责人决定。

## 7. 必须停下并升级的情况

遇到以下情况时停止当前任务，在任务卡评论区写清现象、已尝试的办法和需要的决定，并通知对接负责人。A00 负责跟踪，阻塞超过 1 个工作日时再升级一级。

- 契约有歧义、契约之间互相矛盾，或者实现需要修改已冻结的契约
- 验收用例和需求编号的描述不一致
- 需要修改文件所有权范围之外的文件，或任何接入方仓库中的文件
- 同一门禁连续 2 次未通过
- 需要新增运行时依赖、新增开发依赖，或升级已有依赖的主版本
- 公共 API 需要破坏性变更
- 涉及令牌、密钥、鉴权、脱敏规则、同意管理，或任何个人信息字段
- 需要发布包、访问预发布或生产环境，或者需要生产数据
- 性能、体积或可靠性指标无法达到任务卡的目标
- 发现 D001 或 Q1–Q7 中尚未确认的事项影响本任务的实现
- **工作树缺少本任务所依赖的前置文档**（决策记录、契约变更、门禁配置等——说明派工时序有问题，例如工作树建立之后契约才被更新）。**不要按过期版本实施或测试**：立即报告并要求同步；执行 Agent 不自行执行 git 写操作

不要在升级的同时按自己的猜测继续实现。和这个问题无关的部分可以继续做。

## 11. 编码硬约束

以下约束出自总体方案的设计原则与安全要求。A12 评审时逐条检查，违反任何一条都属于阻断意见。

客户端 SDK：

- 公共方法同步返回，从不向业务抛错；内部异常一律捕获，并在 C08 计数。
- 不读取 Cookie 和业务的 localStorage 键；不向业务的全局错误处理器写入 SDK 自身的错误。
- hook 只包装、不替换原生行为；包装逻辑出错时回退到原函数；销毁后不留下监听、定时器和 hook。
- 所有队列和缓存都有上限（命令队列 200 条，预启动队列 500 条，其余以契约为准）；溢出时优先淘汰 normal 事件。
- 主线程上不出现 50 ms 以上的任务；序列化和压缩要分片执行，或放到空闲时段。
- 用函数式工厂和闭包组织代码，不用类继承；不引入运行时依赖，确需引入时按第 7 节升级。
- 每个丢弃路径都有原因码，并计入 C08。
- 模块顶层不产生副作用（不注册监听、不访问 `window`），保证 tree-shaking 生效，并且可以在 SSR 和 Vitest 环境中导入；包的 `package.json` 声明 `"sideEffects": false`。
- 公共类型和导出只从各包的 `src/index.ts` 暴露；内部模块不对外导出。

开发工具（`tools/`）：

- 只用 Node 内置模块，确需第三方依赖时按第 7 节升级（Q4）。
- M01 只监听 `127.0.0.1`，令牌只做占位值比对；它实现 `receiver-requirements.md` 的“必须”条目，但不得作为生产接收方的参考实现对外提供。
- K02 不得读取、打印或提交私钥内容；测试密钥在测试运行时生成。
- CLI 失败时返回非零退出码，输出可读的错误信息，便于在接入方 CI 中使用。

接收方的约束（只在 202 前持久化、去重、日志不含令牌等）写在 `docs/contracts/receiver-requirements.md`，不在本项目内实现。

通用：

- 不在代码、测试样例和日志里写入真实的个人信息、令牌或密钥；样例数据用占位值。
- 依赖使用锁定版本，提交 `pnpm-lock.yaml`。
- 每个合入请求都要关联任务编号和需求编号。
