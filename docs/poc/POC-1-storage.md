# POC-1 追加轮：离线副本的存储落盘窗口（IndexedDB / OPFS）

- 对应任务：T02（POC-1 投递可靠性）追加轮
- 执行 Agent / 对接负责人：A04 投递 / 前端负责人（结对）
- 日期：2026-10-12（首轮，沙箱内，已作废）／2026-10-13（非沙箱补齐 3 次独立运行并定稿）
- 决策依据：`docs/decisions/D003-critical-reliability-tiered-target.md`（R02 裁定：硬杀场景改为 best-effort，并「在 IndexedDB / OPFS 的落盘窗口验证完成之前，不承诺该场景下的丢失率」）
- 前置报告：`docs/poc/POC-1.md`（三引擎 × 四类场景；本轮沿用同一套 harness 与判定口径）

## 目标与判定标准

**要回答的问题**：POC-1 证明「`localStorage` 预写」在 Chromium / Firefox 上有 0–5 秒且不确定的落盘窗口，硬杀场景下 critical 100% 丢。本轮把离线副本的存储实现换成 **IndexedDB（显式事务 `oncomplete`）** 与 **OPFS（`flush()`/`close()`）**，用同一批强杀场景重测：**落盘窗口能不能压到可接受范围？跨标签页并发写是否更可靠？**

按 D003 第 2 条，硬杀场景**不适用** `critical ≤0.1%`，本轮**不判定丢失率达标**，只报告两件事：**暴露窗口长度**与 **best-effort 存活率**。

### 事先写清的通过标准（本轮判定依据）

| 编号 | 判定项 | 通过标准 |
|---|---|---|
| C1（主判定） | 落盘窗口 | 某存储在 **Δt ≥ 250 ms** 时，**3 次独立运行都 100% 存活**（每格 1000 条样本）→ 判定「落盘窗口 ≤ 250 ms」，即硬杀最多暴露「事件产生后 250 ms 内尚未完成写入」的那部分事件 |
| C2（理想） | 落盘点是否等于持久点 | Δt = 0 时 3 次运行都 100% 存活 |
| C3（对照必须成立） | 对照组自证 | `idb-pending`（写入推迟、观测时未完成）与 `opfs-pending` 在 Δt = 500 / 2500 ms 上 3 次运行都 **0% 存活**；否则对照设计有误，主格结论不可信 |
| C4（跨标签页） | 并发写语义 | 3 标签页并发写（3 轮）**被覆盖 = 0**，且 3 次运行一致 |
| C5（写入成本） | 主线程占用 | 单条 critical 落盘延迟 p50 ≤ 5 ms；100 条/批的批写 p95 ≤ 50 ms |
| C6（配额与失败处理） | 写入被拒 | 写入被拒时计数增长（`prewrite_failed_quota`）且不向业务抛错；真实 `QuotaExceededError` 能否触发如实记录 |
| C7（基线对照） | 必须保留 | 每一栏都要有 `localStorage` 基线；基线与 POC-1 的结论一致（硬杀下大面积丢失） |

采样强度：Δt ∈ {0, 100, 250, 500, 1000, 2500, 4000, 5000} ms，**每格 1000 条样本**（2 次试验 × 500 条），**每格重复 3 次独立运行**，三次结果全部列出（不做平均）。

## 方法

### 与 POC-1 完全一致的部分

- 判定「丢失/存活」口径不变：Node 侧生成确定性 `event_id`（合法 UUID v4），**以 M01 的入库明细为准**；本轮的「存活」= 强杀并重启后能从离线副本读回的条数 / 应有条数（与 POC-1 的 `prewriteSurvival` 同义）。
- 强杀方式不变：`leave.trigger = none`（关闭一切离开钩子），**真 SIGKILL**（Chromium 经 browser 级 CDP 的 `SystemInfo.getProcessInfo` 取浏览器进程 PID；WebKit/Firefox 经 `pgrep` 取进程 PID），同一持久化 profile 重启后读回。
- Δt 的口径：对主格是「**落盘点确认之后**再等 Δt 才强杀」；对照组没有落盘点，Δt 从等待上限之后开始计（结果 JSON 的 `writeInfo` 记录了每次写入是否到达落盘点）。

### 三种存储与四个对照格

| 模式 | 落盘点定义 | 说明 |
|---|---|---|
| `local` | `localStorage.setItem` 返回 | 基线，与 POC-1 相同 |
| `idb` | `IDBTransaction.oncomplete` | 显式事务写入 object store；Promise resolve 即事务完成 |
| `idb-strict` | 同上，但事务带 `{durability:'strict'}` | 观察 `durability` 选项是否改变窗口 |
| `opfs` | `createSyncAccessHandle()` 的 `flush()` + `close()` | 每标签页一个文件 `pending-<tabId>.json`（OPFS 没有原子的共享存储，分文件是正确设计） |
| `idb-pending`（对照） | 无（写入被推迟 60 s） | 自证：未完成的事务在强杀后一定读不回来 |
| `opfs-pending`（对照） | 无（整个写入被推迟 60 s） | 同上 |
| `opfs-noclose`（对照） | — | 已 `write` + `flush`，只把 `close()` 推迟：用来定位 OPFS 真正的持久点 |

### 场景

| 场景 | 内容 | 样本 |
|---|---|---|
| `storage` | 存储 × Δt 的落盘窗口矩阵 | 每格 2 次试验 × 500 条 = 1000 条，3 次独立运行 |
| `storage-multitab` | 3 个标签页**同时**预写到同一个离线副本，读回可见条数 | 每存储 3 轮 × 3 标签页 × 200 条，3 次独立运行 |
| `storage-perf` | 批写耗时（100 条/批，共 1000 条）、单条 critical 落盘延迟、配额估算、写入被拒的处理 | 每存储 1 次（重复 3 次运行） |

## 结论

**主判定 C1（落盘窗口 ≤ 250 ms）：`idb` 与 `opfs` 都通过，`local` 不通过。**

| 判据 | `local`（基线） | `idb` | `opfs` | 判定 |
|---|---|---|---|---|
| C1 主判定（Δt ≥250 ms 三次运行全 100%） | ❌ Chromium/Firefox 不通过 | ✅ 三引擎全通过 | ✅ 三引擎全通过 | — |
| C2 理想（Δt = 0 三次全 100%） | ❌（WebKit 除外） | ✅ **三引擎 Δt=0 就 100%** | ✅ 三引擎 Δt=0 就 100% | — |
| C3 对照自证 | — | ✅ `idb-pending` 全 0/1000 | ✅ `opfs-pending` 全 0/1000 | 测量有效 |
| C4 跨标签页被覆盖 = 0 | ❌ 600–1000/1800 被覆盖 | ✅ **0/1800** | ✅ 0/1800（每标签页一文件） | `opfs-shared` ❌ |
| C5 写入成本 | ✅ | ✅ p50 1–4.1 ms、p95 3–17 ms | ✅ 但 p95 波动大（最高 43 ms） | — |
| C7 基线保留 | ✅ | — | — | — |

**明确判定：`IndexedDB`（显式事务，`oncomplete` 作为落盘点）在三个引擎上都把硬杀窗口压到 0**——Δt = 0 时三次独立运行全部 100% 存活。这直接推翻 POC-1 对 `localStorage` 的那个「0–5 秒且不确定」的窗口：**问题出在 `localStorage` 这个存储，不出在「预写」这个方案**。

其余要点：

1. **`OPFS` 同样能压到 0**（Δt = 0 三引擎全 100%），且每标签页一个文件时并发写零覆盖。但它的持久点是 **`flush()`**（`opfs-noclose` 对照在 Δt=0 就 100% 存活），实现上要多一个 worker，且批写 p95 明显更抖（最高 43 ms，`idb` 最高 17 ms）。**「多标签页共享同一个 OPFS 文件」会丢数据（600–800/1800），绝对不能用这种设计。**
2. **`localStorage` 必须从离线副本方案里排除**：Chromium 与 Firefox 在 Δt ≤4000 ms 时存活为 0，Firefox 连 5000 ms 都只有 500–1000/1000——与 POC-1 一致，说明 POC-1 的结论稳健。
3. **`durability: 'strict'` 没有可观测差别**（`idb-strict` 与 `idb` 都是 100%，耗时略高）。**不要为此增加复杂度**。
4. **写入成本可接受**：`idb` 批写（100 条）p50 1–4.1 ms、p95 3–17 ms；单条落盘 p50 1–2 ms。因此改用 IndexedDB 之后，硬杀场景的残余暴露窗口 = 「事件已产生但事务尚未完成」的那一小段，量级是**毫秒**，而不是秒。

## 局限

1. **必须记录的一次方法学修正（首轮数据已作废）**：首轮（2026-10-12）在 DSH 文件沙箱**内**运行，WebKit 的 OPFS 格子**每一次写入都失败**（`writeInfo[].resolved = false`，错误 `The operation failed for an unknown transient reason (e.g. out of memory)`），当时被误读为「OPFS 在 WebKit 上不可用」。**该结论已撤回**：沙箱阻塞了 WebKit 写 `~/Library/WebKit/…` 与 `~/Library/Caches/org.webkit.Playwright/…`，属**沙箱造成的写入失败，不是持久化语义**。本轮全部在非沙箱 shell 重跑，WebKit 的 OPFS 写入全部 `resolved = true` 并 100% 存活。
   **可复用的教训**：① 浏览器存储的持久化测量**必须在非沙箱环境做**；② harness 必须逐次记录「写入是否到达落盘点」（`writeInfo[].resolved` 与 `durableResolved`）——正是这两个字段让这次误判被发现。
2. **harness 的进程清理缺陷**：三引擎 × 3 次独立运行的全量扫掠中，WebKit 的辅助进程（GPU / WebContent / Networking xpc）会随每个 profile 的浏览器重启累积，实测一度达到数百个，**导致第三次运行的 WebKit 卡死**。处置：终止该次运行、清理泄漏进程、单独补跑 WebKit 一轮（`results-storage-v2/2026-10-13T03-32-49-076Z`）。**T16/T29 若复用本 harness，应在每个格子之后清理浏览器进程。**
3. **驱动/浏览器版本偏离**（与 POC-1 同）：仓库锁定 `@playwright/test` 1.64.0，实际用树外只读 `playwright-core` 1.60.0 + chromium-1223 / firefox-1522 / webkit-2287。`localStorage` 与 OPFS 的落盘行为属**实现细节**，跨版本可能变化；**T29 应在锁定版本上复测关键结论**（尤其是「IndexedDB Δt=0 即持久」这一条）。
4. **`QuotaExceededError` 未构造出来**（判据 C6 未完全验证）：三引擎报的配额估算都在 ~19.6 GB 量级，本轮没有把它耗尽。因此「写入被拒时计 `prewrite_failed_quota` 且不向业务抛错」这条**只有代码路径，没有实测证据**，属未验证项。
5. **采样粒度**：每格 2 次试验 × 500 条，存活数只能以 500 为步长出现（例如 Chromium `local@0ms` 第三次运行为 500/1000，表示两次试验只有一次落盘）。这足以判定「100% / 非 100%」，但不足以刻画窗口边界的精细形状。
6. **未复测 POC-1 的其余场景**：本轮只重跑了强杀 + 跨标签页并发 + 写入耗时；页面离开、断网、多标签页补发选主仍以 POC-1 的 `localStorage` 结论为准。改用 IndexedDB 后这些场景的重复补发率、离开预算**没有重新测量**。
7. 未覆盖：真实用户态强杀（系统内存压力、标签页被系统回收）、`bfcache`、无痕/隐私模式下的存储清退、存储压力下的自动驱逐（eviction）、以及非 Playwright 的真机 Safari。

## 对 T16 的建议

1. **离线副本改用 `IndexedDB`，并把 `transaction.oncomplete` 作为唯一落盘点**。只有 `oncomplete` 返回之后，事件才可以被认为「在硬杀下不会丢」；此前的一律按在途处理。这是本轮最重要的一条。
2. **不要用 `localStorage` 存 critical 离线副本**（Chromium/Firefox 的 0–5 秒窗口是 POC-1 与本轮共同确认的）。`localStorage` 仍可用于非持久的小状态（会话随机数等）。
3. **不要用「多标签页共享单个 OPFS 文件」**（实测被覆盖 600–800/1800）。若选 OPFS，必须每标签页一个文件，且以 `flush()` 为持久点（`close()` 不是）。
4. **不要为 `durability: 'strict'` 增加复杂度**：与默认无可观测差别。
5. **保留 POC-1 的「critical 立即微批发送」设计**：IndexedDB 把持久化窗口消掉了，但「已产生但尚未提交」的那几毫秒仍然敞口；立即发送进一步缩小它，并降低对本地存储的依赖。
6. **写入节流**：`idb` 批写（100 条）p95 最高 17 ms 属可接受；但仍应避免每条 critical 单独开事务，按批提交（建议 100 条或 200 ms 取先到者）。
7. **跨标签页**：IndexedDB 并发写零覆盖，因此**正确性不再依赖选主**；选主仍然需要，但目的变成控制**补发流量**（POC-1 实测不选主时重复 ≈2 倍离线副本流量）。沿用 POC-1 的 Web Locks 优先、BroadcastChannel 需 settle ≥50 ms 的结论。
8. **原因码（需契约变更请求，尚未确定）**：`prewrite_failed_quota` 的计数路径本轮没有实测触发（见「局限」第 4 条），T16 落地时必须补上并纳入 C08 计数。

## 与 D003 的一致性

D003 第 2 条当前写的是：硬杀场景**不适用** `critical ≤0.1%`，改为 best-effort，并「在 IndexedDB / OPFS 的落盘窗口验证完成之前，不承诺该场景下的丢失率」。**本轮的验证已完成**，因此建议按下述方向**修订 D003 第 2 条**（需项目负责人批准，本报告不代替该批准）：

> 硬杀场景（SIGKILL、进程被回收、标签页被丢弃、渲染进程崩溃）**不再只是 best-effort**：使用 **IndexedDB 且以 `transaction.oncomplete` 为落盘点**时，**已确认落盘**的 critical 事件在三个引擎的硬杀实测中均不丢失（Δt = 0，三次独立运行全 100%）。残余暴露窗口 = 「事件已产生但事务尚未提交」，其长度由批写提交延迟决定（实测 p50 1–4.1 ms、p95 3–17 ms），**不再是原来那个 0–5 秒且不确定的窗口**。因此：
> - 要求 T16 **以 IndexedDB 作为离线副本存储**，禁止用 `localStorage` 存 critical 副本；
> - 对「已确认落盘」的 critical 事件，硬杀场景**可以承诺不丢**；对「尚未提交」的部分按暴露窗口计量，并单独计数；
> - 原「硬杀不适用 0.1%」的表述应改为「硬杀场景按**暴露窗口**（毫秒量级）而非丢失率计量」。

其余部分（有优雅退出路径的场景仍适用 0.1%；normal 的 1% 口径边界；重复 ≈1 倍 critical 流量计入容量）**与 D003 一致，无需改动**。
