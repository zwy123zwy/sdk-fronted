## 建议的公共 API

| 方法 | 用途 | 对应需求 | 核对状态 |
|---|---|---|---|
| `init(options)` | 初始化：应用标识、令牌、端点、配置端点与公钥、环境、版本、初始同意状态、插件 | C01-F1、C03-F1 | 待核对签名 |
| `track(name, { dimensions, metrics, attachment })` | 上报自定义事件 | C01-F1、C01-F4 | 待核对签名 |
| `log(level, message, { dimensions })` | 上报日志 | C01-F1 | 待核对签名 |
| `captureError(error, { dimensions })` | 手动上报错误 | C05-F1 | 待核对签名 |
| `setUser(id, { hashed })` / `clearUser()` | 设置与清除用户 | C04-F1 | **待核对**（实际签名形式可能不同） |
| `setContext(key, value)` / `removeContext(key)` | 全局自定义上下文 | C04-F3 | 待核对签名 |
| `setPage(pageId)` | 手动路由模式下设置页面 | C05-F3 | 待核对签名 |
| `configureView(...)` | 配置页面归属/视图（初稿未列出） | C05-F3、C04-F2 | **待核对**（由 T14 交付，需确认它是接入面还是装配面） |
| `setConsent(state)` | 设置同意状态 | C04-F5 | 待核对签名 |
| `flush()` | 立即冲刷 | C06-F2 | 待核对签名 |
| `destroy()` | 销毁 | C02-F1 | 待核对签名 |
| `createClient(options)` | 创建独立实例 | C01-F5 | 待核对签名 |

所有方法同步返回，从不抛错（C01-F1）。

## 场景

「验收」一列给出**覆盖该场景的验收文件**；**具体 AC 编号待逐条填入**（本轮执行受"不得先读文件"的约束，未打开验收文件——不凭印象写编号）。

| 编号 | 场景 | API 表达 | 涉及需求 | 验收（文件） |
|---|---|---|---|---|
| UC-01 | 应用启动后自动采集错误、性能、页面浏览、HTTP，并按规则过滤 | `init` 时启用插件；过滤规则由远程配置 `sampling.rules` 与插件 `options` 下发 | C05-F1 至 F4、C03-F4 | `tests/acceptance/C05.md`（AC 编号待填） |
| UC-02 | 用户登录后设置用户，退出后清除；匿名阶段的事件不关联用户 | 登录回调中 `setUser`，退出时 `clearUser` | C04-F1 | `tests/acceptance/C04.md` |
| UC-03 | 业务完成一个关键动作（如提交任务），要求可靠送达 | `track('task_submit_complete', ...)`；投递等级由字典声明为 critical | C07-F5、Q3 | `tests/acceptance/C07.md` |
| UC-04 | 页面内高频的业务操作轨迹（每秒数十条），会话结束时也要尽量送达 | 每个动作 `track`；离开页面时由 SDK 自动冲刷，业务在提交按钮处可以调用 `flush` | C06-F2、C07-F1 | `tests/acceptance/C06.md`、`C07.md` |
| UC-05 | 媒体播放指标：开始播放、拖动、卡顿、首帧耗时 | 每类动作一个事件名，耗时放 `metrics`，例如 `track('video_play_stall', { metrics: { stall_ms } })` | C01-F1 | `tests/acceptance/C01.md` |
| UC-06 | 接入方用 K02 签名一份调低采样率、关闭某个插件的配置并发布到自己的静态资源服务，10 分钟内生效 | 无需业务代码改动；远程配置下发 | C03-F3 至 F5 | `tests/acceptance/C03.md`、`K02.md` |
| UC-07 | 用户在隐私设置中拒绝"体验改进"，之后又同意 | 接入方的同意组件回调 `setConsent('denied')` / `setConsent('granted')` | C04-F5、Q5 | `tests/acceptance/C04.md` |
| UC-08 | 迁移期与已有第三方 APM 并行运行，自定义事件双写 | `init` 时注册双写适配器，并注入第三方的上报函数 | C05-F5、Q7 | `tests/acceptance/C05.md`、`C08.md` |
| UC-09 | 单页应用使用自定义路由，路由库不触发 History 事件 | 关闭自动路由，在路由守卫中调用 `setPage` | C05-F3 | `tests/acceptance/C05.md` |
| UC-10 | 微前端：主应用与子应用分别上报到不同应用 | 子应用用 `createClient` 创建独立实例 | C01-F5 | `tests/acceptance/C01.md` |
| UC-11 | 静态页面没有构建流程，需要尽早捕获首屏错误 | 头部内联加载桩，之后通过命令队列调用 | C01-F2、C01-F3 | `tests/acceptance/C01.md` |
| UC-12 | 开发者排查"为什么我的事件没上报" | 开发环境通过 URL 参数开启调试模式 | C08-F4 | `tests/acceptance/C08.md` |

## 无法用现有公共 API 表达的场景（初稿第 3 项待补充）

**结论：发现 1 处候选缺口，需要负责人拍板（见问题 5）。**

| 候选缺口 | 现象 | 为什么算缺口 |
|---|---|---|
| **行为面包屑** | T18 的任务卡明确写了"行为面包屑不记录输入框内容"这条隐私约束，但本表的 12 个场景**没有任何一个涉及面包屑**，公共 API 表里也没有对应的表达方式 | 要么面包屑是错误事件内部的自动上下文（那它应当在 UC-01 的期望行为里写清，并明确"由 SDK 自动采集、无独立 API"），要么它是一个需要 API 的独立能力（那当前设计缺一条 API）。**二者必居其一**，需要明确 |

其余 12 个场景均可由现有 API 表达。**未发现需要新增 API 的场景**——即本表不构成对 `etc/*.api.md` 的增补请求。

## 需要负责人拍板的问题

> 以下问题**必须在 T18 开工前定**，否则实现会建立在未确认的假设上。每条都给了我的建议，**建议不等于结论**。

1. **逐行核对 API 签名**：初稿的「API 表达」是建议形态，而 T12 已冻结正式签名（`packages/*/etc/*.api.md`）。**请确认由谁、在何时完成逐行对齐**（我的建议：由 T18 执行方在实施计划 M0 阶段完成，把差异逐条列给负责人，而不是现在凭印象改本表）。
2. **UC-05 的请求体边界**（若 C05-F4 涉及请求体）：任务卡硬约束是"请求体默认不采集"。**是否提供显式开关**让接入方在知情下采集？我的建议：**不提供**，需要时走"接入方自己上报"的路径。
3. **UC-03 的"关键事件"由谁定义**：我的建议：**接入方在字典/`track` 时显式声明**，SDK 不替业务判定重要性。
4. **UC-09 的路由来源**：我的建议：**接入方在路由变化后调用 `setPage`/`configureView`**，SDK 不主动打补丁 `history`（避免破坏宿主框架且难以回退）。
5. **面包屑的归属**（见上一节）：是错误事件的自动上下文，还是独立能力？
6. **AC-15..18 的归属**：`tests/acceptance/C05.md` 有 20 条 AC，任务卡只列了 16 条（漏 AC-15..18），而这 4 条正是 T19 报告里记为"需用真实 `createKernel` 重驱动"的部分。**请确认它们是否属于 T18。**
7. **装配根归属**：没有任何任务卡认领 `packages/browser` 的装配接线（"把所有模块接起来、让事件真的发出去"）。**本表按"装配已存在"描述期望行为**（UC-01 期望"自动上报"）；若装配根不在 T18 范围内，请指定归属，否则多数场景**无法端到端验证**。
